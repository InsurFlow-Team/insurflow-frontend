# Role & Permission Matrix (Masar MVP)

Source of truth for agreed role decisions. Update this file whenever a new ruling is agreed — decisions must not live only in chat history.

## Roles
- `ADMIN`
- `CLAIMS_OFFICER`
- `FIELD_ADJUSTER` — blocked from the dashboard entirely (at login)

## Matrix (frontend intent)

| Capability | ADMIN | CLAIMS_OFFICER | FIELD_ADJUSTER |
|---|---|---|---|
| View Overview / Claims Queue / claim details | yes | yes | no access |
| Create claim (`POST /claims`) | yes (intent) | yes | no |
| Assign field adjuster (`POST /claims/:id/assign`) | yes (intent) | yes | no |
| Decide claim — `POST /claims/:id/decision` (UNDER_REVIEW → APPROVED/REJECTED), Approve/Reject buttons in the **Decision / Closing section** | yes | **no** (CO reviews + exports only; final decision is ADMIN's) | no |
| View Settings + User Management | yes | no | no |
| Manage users (add / edit / status (deactivate/activate) / reset) | yes | no | no |
| View own Profile (`/profile`) | yes | yes | no access |
| View Field Adjusters Directory (`/adjusters`) + Profile (`/adjusters/:adjusterId`) | yes | yes | no access |
| View adjuster **Work history** on the profile (completed claims, inspection count, turnaround) | yes | yes | no access (no dashboard access) |
| View Dashboard **Needs-attention queue** (blocked claims + who blocks each) | yes | yes | no access (no dashboard access) |
| View Dashboard **Adjuster capacity** (spare slots vs claims awaiting assignment) | yes | yes | no access (no dashboard access) |

## Frontend enforcement points
- The "Awaiting Decision" attention group is visible to **both** ADMIN and CO because it is a *read* queue, but the decision itself stays ADMIN-only (`ClaimDetails.tsx` gates the FinalDecision panel to ADMIN). The queue tells a CO "this is waiting on an admin"; it does not let them act on it.
- `dashboard/src/App.tsx:28` — RoleGuard `["ADMIN","CLAIMS_OFFICER"]` for `/dashboard`, `/claims`, `/claims/:claimId`, `/adjusters`, `/adjusters/:adjusterId`, `/map`, `/profile`.
- `dashboard/src/App.tsx:38` — RoleGuard `["ADMIN"]` for `/settings` + `/settings/users`; `App.tsx:44` `/users` redirects to `/settings/users`. The password card lives on **Profile** (all dashboard roles), NOT in Settings.
- `dashboard/src/App.tsx` — `/unauthorized` route inside ProtectedRoute/DashboardLayout (any authenticated user), renders the Access Denied page.
- `dashboard/src/routes/RoleGuard.tsx` — a role not in the allowed list → `Navigate to "/unauthorized"` (visible Access Denied page, no silent redirect).
- `dashboard/src/layouts/Sidebar.tsx:33,39` — Overview/Claims Queue → ADMIN+CO; `Sidebar.tsx` "Field Adjusters" → ADMIN+CO; `Sidebar.tsx` "Map Dispatch" (`/map`) → ADMIN+CO; `Sidebar.tsx:51` Profile → ADMIN+CO; `Sidebar.tsx:59,61` — Settings/User Management → ADMIN only.
- `dashboard/src/components/notifications/NotificationBell.tsx` (2026-09-27) — the header notification bell has **no RoleGuard of its own**, and does not need one: the whole `DashboardLayout` is already behind the `["ADMIN","CLAIMS_OFFICER"]` guard, and `Login.tsx` blocks FIELD_ADJUSTER from this web app entirely, so the bell is reachable by exactly ADMIN + CLAIMS_OFFICER. Notifications are per-recipient — `GET /notifications` only ever returns the caller's own (AD-001 had 14, CO-001 had 11, same organization) — so this is not a cross-user leak.
- Two of the eight documented notification types (`PENDING_ACCEPTANCE`, `CORRECTION_REQUIRED`) are **adjuster-facing**, so they will only reach a user once the mobile app ships. The web bell must keep rendering them as neutral rows (it does — the icon/tone lookup falls back), and the click still routes to `/claims/${relatedClaimId._id}`, which a FIELD_ADJUSTER cannot open. Accepted for now: that user marks the row read and stays put, which beats an `/unauthorized` bounce. Revisit if an adjuster-facing surface is ever added.
- `dashboard/src/pages/Login.tsx` — FIELD_ADJUSTER blocked (see `AuthContext.tsx`); every allowed role lands on `/dashboard` after login.
- `dashboard/src/pages/Users.tsx:311` — self-row protection: deactivate/activate hidden on own row (`currentUser?.id`); Reset allowed on own row. No Delete action exists (decision 2026-09-19).
- `dashboard/src/pages/ClaimsList.tsx:76` — per-row Assign action available to `ADMIN` + `CLAIMS_OFFICER` (assign only from `NEW` status).
- `dashboard/src/pages/ClaimDetails.tsx` — Assign Field Adjuster button (same `ADMIN`+`CLAIMS_OFFICER` gate) offered only while the claim is `NEW`; after success the detail reloads (status becomes `PENDING_ACCEPTANCE`).
- `dashboard/src/pages/ClaimDetails.tsx` (2026-09-26) — **Approve/Reject decision buttons** live in the **Decision / Closing section** (`sections/DecisionSection.tsx`), shown next to the "لم يتم اتخاذ قرار أو إغلاق المطالبة بعد." empty state ONLY while `claim.status === "UNDER_REVIEW"` AND the logged-in role is **ADMIN** (user ruling: the final decision is the admin's — CLAIMS_OFFICER reviews with Start Review and exports the PDF after the admin decides, but never approves/rejects); each button opens a ConfirmDialog then `POST /claims/:id/decision` with `{ decision: "APPROVED" | "REJECTED" }` via `api/claims.decision.ts`; on success the detail reloads (status becomes `APPROVED`/`REJECTED` → the export button unlocks).
- `dashboard/src/pages/AdjusterDetails.tsx` — **Work history** (2026-09-26): the section is no longer a placeholder. It loads independently of the profile (a failure there never blanks the page) and renders four tiles (Completed claims, Total inspections, Avg. turnaround, Last completed) over a `DataTable` of this adjuster's finished claims, each row linking to `/claims/:id`. Visible to **ADMIN + CLAIMS_OFFICER** (the whole profile is behind that RoleGuard). Derivation lives in `src/utils/adjusterHistory.ts` (pure, tested) and `src/api/adjusterHistory.ts`; a claim is "completed" when `APPROVED | REJECTED | CLOSED`, the inspection count counts every `Inspection Started` event performed **by that adjuster** (a revisit counts twice), and the completion time comes from `closedAt` else the decision event — **never** `updatedAt`. Anything needing the timeline is `null` → rendered "—" rather than guessed, and the detail fan-out is capped at 25 with an explicit "showing the N most recent" note.
- Capacity override UI (2026-09-19): `AssignClaimModal` + `AddClaimModal` show a "Capacity Override" ConfirmDialog when the backend answers `409 ADJUSTER_UNAVAILABLE`; confirming resends the same assignment with `overrideCapacity: true`. Declining keeps the claim unassigned (and lists it as created-but-unassigned from Create+Assign).
- Map Dispatch (`/map`, updated 2026-09-24): `MapPage` (ADMIN+CO) is the app's main map; the Create Claim intake ALSO has a map again (see create ruling below — `PreciseLocationSection` + `LocationMapPicker` restored). Default center is the **West Bank** (`[31.9, 35.3]`, zoom 10). Claim pins are **teardrop markers** (distinct from the square adjuster dots) colored by status; adjuster pins by backend availability/status — never a hardcoded capacity. Text-only claims (no `incidentCoordinates`) must NEVER render an invented pin — their reported-incident text is surfaced in the claim popup ("موقع الحادث المُبلغ عنه") and the dispatch panel from `GET /claims/:id` (the list endpoint has no `incidentLocation`, so the page fetches details on selection — single source of truth). Assign from a claim pin, or from an adjuster popup's "اختيار المعاين", reuses `AssignClaimModal`; picking an adjuster on the map preselects the **same id** in the modal, and the modal **consumes the map's claim-scoped dataset** (pins + dropdown = ONE `GET /users/adjusters?claimId=`) — it never starts a second fetch (`useFieldAdjusters(claimId, enabled=false)` when preloaded). Only `NEW` claim pins show Assign; after success the map refetches `GET /claims`. `distanceKm` is rendered from the backend value/order only — never computed client-side. Adjusters with `location: null` appear in the list with "الموقع غير متوفر" (no pin). Leaflet (react-leaflet 5) is lazy-loaded with the `/map` chunk.
- **DEMO mode (2026-09-24, user ruling)**: an OPT-IN, OFF-by-default toggle on `/map` ("DEMO Locations", persisted in `localStorage "masar.map.demo"`, never shown unless toggled). While active, a live adjuster that the backend reports WITHOUT a location receives a **simulated West Bank position** (round-robin over نابلس/رام الله/بيت لحم/جنين/الخليل) and a claim-relative **client-side haversine distance** (`utils/demo.ts`); the nearest adjuster is surfaced in the dispatch panel and the adjuster list sorts by distance. Everything simulated is tagged **DEMO** in the UI (amber chip on the panel/list, banner on top of the page) and is **never sent to the backend**; it **never overwrites** an adjuster that already has a real location, and claims never get invented pins even in demo. Real GPS for adjusters is still a **backend/mobile handoff** (adjuster mobile app) — once `/users/adjusters` returns coordinates+distanceKm, demo becomes unnecessary.

## Backend reality (verified live — do NOT assume otherwise)
- `PATCH /users/:id/status` — admin-only; CLAIMS_OFFICER → 403 (proven).
- `POST /claims` and `POST /claims/:id/assign` — CLAIMS_OFFICER passes (400-validation proves authz). ADMIN blocked with 403 was confirmed live earlier; محمد (backend owner) has since allowed ADMIN to create+assign (per user confirm) — re-verify live with current admin credentials before trusting UI-only.
- `POST /claims/:id/decision` (verified live 2026-09-26 with CO-001) — body `{ decision: "APPROVED" | "REJECTED", notes?: string }`. The field is **`decision`**, NOT `status` (sending `status` → 400 Validation Error "Decision is required" + `"status" is not allowed"). Precondition: claim must be `UNDER_REVIEW` else `409 INVALID_STATUS_TRANSITION` ("Claim is not in UNDER_REVIEW status"). There are NO dedicated `/approve`, `/reject`, or `/decide` routes (all `404 Endpoint Not Found`). CO token passes authz (409 status-precondition proves it). The demo flow is impossible without this step: ... → review/start (SUBMITTED→UNDER_REVIEW) → decision (→APPROVED/REJECTED) → export PDF.
- Assignment round-trip (verified live 2026-09-19): `POST /claims/:id/assign` → `200` `PENDING_ACCEPTANCE` ("Assignment pending acceptance") with timeline event. `accept-assignment` / `decline-assignment` / `inspection/start` / `inspection/submit` exist and are adjuster-only (CO → 403). `review/start` validates `SUBMITTED` only (409 otherwise). Declined-claim resulting status + reason validation NOT yet verified (needs a demo adjuster credential); `PENDING_ACCEPTANCE` proves NOT counted in `activeTasksCount`.
- Capacity override (verified live 2026-09-19 on FA-009, 4 tasks > capacity 3): assign → `409` with `errors[].code = "ADJUSTER_UNAVAILABLE"` (live message text: "Adjuster is currently unavailable"). Resending the same payload with `overrideCapacity: true` → `200` `PENDING_ACCEPTANCE`, and the timeline records `[CAPACITY OVERRIDE] Assigned while adjuster had 4 active tasks (max: 3)`. Reassigning a claim that is already `PENDING_ACCEPTANCE` → `409 INVALID_STATUS_TRANSITION` ("Claim is not in NEW state") — assignment is only ever offered from `NEW`. **Contract confirmed by backend owner (2026-09-20)**: `ADJUSTER_UNAVAILABLE` means capacity ONLY (→ override dialog); `ADJUSTER_NOT_FOUND` means the adjuster identity is gone and NO override is ever offered (inline error + stale adjuster disappears on reload). Decline is `PENDING_ACCEPTANCE → NEW` and the **Web has no Accept/Decline UI**. Frontend keys the override strictly on `ADJUSTER_UNAVAILABLE` (`getApiErrorCode` reads `errors[0].code`).
Assign action on the **Claims list** (2026-09-24): no modal — it navigates to `/map?claim=<id>` (deep link); MapPage **selects that claim and shows its dispatch panel (nearest adjuster + distances)** — the assign form is **never auto-opened**; the officer reviews who is nearest, then presses **Assign** on the panel to open the form. The `?claim=` param is consumed once (`setSearchParams({}, { replace: true })`) so Refresh never re-selects it. ClaimDetails keeps its inline modal. Assign action on the Claims list → ASSIGNED asserts only when claim is **NEW**. 
- Assign dropdown ACTIVE-only (2026-09-20): both `AssignClaimModal` and `AddClaimModal` slice `adjusters.filter(a => a.status === "ACTIVE")` — the backend refuses to assign INACTIVE (→ `404 ADJUSTER_NOT_FOUND`), so deactivated users are never offered. Live `/users/adjusters` (CO token, 2026-09-24, re-verified from Field Adjusters Directory live view) = 6 rows: **ACTIVE → FA-001 Ahmed Adjuster 1/3, FA-002 Second Adjuster 1/3, FA-003 hammod 2/3, FA-009 Ruba 4/3** (Ruba was re-activated between 2026-09-20 and 09-24; 4/3 → `Unavailable`/Busy); **INACTIVE → FA-004 hammod 1/3, FA-005 newUser 0/3**. NOTE: two users are literally both named "hammod" (FA-003 ACTIVE vs FA-004 INACTIVE). The dispatch list header says "Active Adjusters (N)" — N counts ACTIVE (incl. Busy ones), it is NOT "available". Assign labels now render `name (code) — Available/Busy · x/3` so the duplicate is distinguishable. OPEN: if the admin Users page shows FA-004 as ACTIVE while `/users/adjusters` says INACTIVE, that is a backend endpoint disagreement → report to محمد (GET /users is admin-only; CO → 403, so the decision must be live-reverified with an admin token).
- `GET /users/adjusters` — returns `availability` + `activeTasksCount` + **`capacityLimit: 3` lived** (verified every adjuster; 4 tasks → UNAVAILABLE). No simulation in the normal path anymore (only the opt-in DEMO mode above produces simulated positions, clearly tagged). `location` (GPS) is now **real** for live adjusters (verified 2026-09-26: FA-001 `32.2603475, 35.1288667` updatedAt 2026-09-26, FA-002 `31.9038, 35.2034`; the earlier "null for every live adjuster" state is **stale**) and `GET /users/adjusters?claimId=` works and returns a per-claim `distanceKm` (verified live: claim 0051 → 16.08 / 34.33 km, 0050 → 12.85 / 35.38, 0047 → 14.91 / 46.17 — the distance genuinely changes with the claim coordinates, so the backend is NOT the cause of a "constant distance"). The frontend maps `location`/`distanceKm` onto `FieldAdjuster` and `incidentCoordinates` onto `ClaimSummary` as optional GeoPoints (`utils/geo.ts` → `normalizeGeoPoint`) and renders "الموقع غير متوفر" in the dispatch list when there is no location. `GET /claims` rows carry `assignedTo: { id, name }` (also normalized in `api/claims.transform.ts`), which is what the adjuster Work history filters on. Live claims created during the text-only window (2026-09-24) can still carry empty `incidentCoordinates` — the map surfaces them by text + amber warning, never an invented pin. NEW claims (restored ruling) always carry the officer-pinned coordinates. `GET /claims` accepts **only** `status`; every other query param (`assignedTo`, `assigneeId`, `adjusterId`, `assignedAdjusterId`, `adjuster`) is rejected with **400** (probed live 2026-09-26) — hence the client-side work-history derivation. Server-side geocoding (text→coords, §7) is **SUPERSEDED** — the officer pins manually now.
- **Claim intake gate (2026-09-21 user ruling; verification endpoint LIVE since 2026-09-24)**: claim creation is a two-step flow. "Add Claim" (ClaimsList) opens `PolicyVerificationModal` first — Policy Number input + "تحقق من الوثيقة" (loading/error states); only after a successful check does the user see "متابعة تسجيل الحادث", which opens the existing `AddClaimModal`. A failed verification NEVER opens the intake form and never calls `POST /claims`. The verification call goes through the single seam `verifyPolicy(policyNumber)` in `src/api/policy.service.ts`, which calls the **live `POST /policies/verify`** returning `{ isEligible, policy: {id, policyNumber, status, startDate, expiryDate}, vehicle: {id, plateNumber, make, model, year, color}, customer: {id, fullName, phone} }` (matches frontend types); unknown policy → `404 POLICY_NOT_FOUND` with `errors[0].code`. No mock since 2026-09-24.
- Create claim → incident location is collected as BOTH a **place description** (`incidentLocation` free text, e.g. "شارع الملك فهد") and a **MANDATORY map pin** the officer drops on the intake map (2026-09-20 ruling, **RESTORED 2026-09-24 — REVERSES the text-only ruling**). `POST /claims` receives `{ policyId, plateNumber, incidentType, incidentLocation, incidentDate, latitude (number), longitude (number) }` — the pin is required, the form cannot submit without it. No `navigator.geolocation` (auto-location stays the mobile adjuster's job). `PreciseLocationSection.tsx` + `LocationMapPicker.tsx` restored. `toCreateClaimRequest` converts the form strings to numbers and throws if either is missing/invalid. New claims render a pin on the dispatch map immediately (backend echoes `incidentCoordinates`). Server-side coordinate enforcement on `POST /claims` is an ACTIVE hardening handoff to محمد (§5), and geocoding (§7) is superseded.
- Live probes use `DEMO-INS` org: `CO-001`/`Password123!` works; `AD-001`/`FT-001` current passwords unknown (login 401).
- `POST /users` (Create User): `ADMIN` rejected → 400 `"role" must be one of [CLAIMS_OFFICER, FIELD_ADJUSTER]` (confirmed live 2026-09-13). Create User form intentionally hides ADMIN.
- Duplicate `employeeCode` on `POST /users` → `409` `EMPLOYEE_CODE_TAKEN` "An employee with this code already exists in your organization".
- Hard delete user — **NOT implemented** (verified live 2026-09-19: `DELETE /users/:id`, `POST /users/:id/delete` and `GET /users/:id` all → `404`. `PATCH /users/:id/status` + `reset-password` exist, admin-only (CO → 403)). Decision: no delete in the product — deactivate (soft) only; claimed user references (`assignedTo`/`performedBy`) must never dangle.
- Notifications — **backend LIVE, 200 OK (re-verified 2026-10-03; supersedes the 2026-09-19 `404`)**: both `GET /notifications` and `GET /notifications/unread-count` respond 200. The frontend consumes them today (`useNotifications` + `NotificationBell`, 22 tests) with per-recipient data — reachable only by ADMIN + CLAIMS_OFFICER (see the bell note above). No permission change; the old "404, no frontend work" line was stale.
- **Claim Details page (2026-09-23, user ruling)**: the detail page now renders the full backend contract — reported incident location (`incidentCoordinates`) displayed separately from the field inspection location (`location`, "بانتظار وصول المعاين وتحديد موقع المعاينة" when null), plus Evidence / Signature / Decision / Timeline sections with Arabic empty states. `GET /claims/:claimId` is the single source of truth (no per-section fetches). Web keep-as-is ruling: `FIELD_ADJUSTER` REMAINS blocked from the dashboard including `/claims/:claimId` (RoleGuard `["ADMIN","CLAIMS_OFFICER"]`). The backend/mobile contract may expose claim details to the adjuster app — that is adjuster-side, not the web dashboard. Any future change to allow adjusters into the web dashboard is a NEW ruling and must update this table.

## Rules of engagement
- Never assume a permission: verify live with both ADMIN and CLAIMS_OFFICER tokens (PowerShell probe pattern — login, then call endpoint; classify 401/400/403/404; read response body).
- UI capability must not exceed what the backend actually allows. When the backend blocks a role (e.g., admin create), either (1) agree a fix with the backend owner, or (2) align the UI.
- Every route/guard change must update this table.
